# CLAUDE.md

**This repository holds the original local app, moved out of the main Home Attic project (see README.md).** The text below was written for the combined
repository; the parts about the cloud relay, home agent, admin console and iPhone app (`backend/relay`, `backend/home_agent`, `backend/admin_service`,
`admin-frontend`, `ios/`) describe code that now lives in the main repository and is not here.

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Copies photos/videos/files from an iPhone into a library folder, with a web UI to browse and import them. FastAPI backend (`backend/app`) + React/Vite frontend (`frontend`). See `docs/README.md` (the index), `docs/guides/ADMIN_GUIDE.md` for setup and running, `docs/project/FEATURES.md` for what is built and how far it was tested, `docs/project/PENDING.md` for what is left, and `docs/guides/DEVELOPER_GUIDE.md` for contracts and decisions.

Intended deployment: the backend and an nginx web container run in **Docker on the Windows PC**; the media lands in `C:\Senthil Krishna\iPhoneLibrary`. A Linux container can't reach an iPhone, so phones get in by one of three routes: the **Mac agent** (`backend/mac_agent`, runs on a Mac with the phone plugged in and uploads over HTTP), the **Safari upload page** (`frontend/public/upload.html`), or a **native Windows backend** (`start.ps1`) that reads the phone over USB/Wi-Fi sync. All three end up in the same library layout and catalogs.

## Commands

From the repo root (PowerShell on Windows; `start.sh` and `.venv/bin/python` on macOS/Linux):

./start.sh [--lan] [--build]                 # same on macOS/Linux
docker compose -f deployment/docker-compose.yml up -d --build   # backend :8765 + nginx web UI :8081
cd backend ; .venv\Scripts\python -m pytest                              # all tests (fake iPhone)
cd backend ; .venv\Scripts\python -m pytest tests/test_api.py -k <name>  # single test

cd backend ; python -m tools.make_test_vectors                           # regenerate Swift crypto test vectors (after any relay/crypto.py change)

cd backend ; python -m mac_agent --server http://<pc>:8765 --token <t> [--dry-run --kinds photos --since YYYY-MM-DD --dest "Trips/Goa" --force]

iOS app tests (simulator): `xcodebuild test -project ios/PhoneBackup.xcodeproj -scheme PhoneBackup -destination 'platform=iOS Simulator,name=iPhone 14'` (needs a Mac with Xcode; SYNC_NOTES logs report these runs on the iPhone 14 simulator).

Setup quirks: Python **3.13** (not 3.14); `pymobiledevice3` is installed with `--no-deps` on purpose (optional deps need a C++ compiler and are unused); `pywin32` is Windows-only via a marker in `requirements.txt`. There is no linter and no frontend test suite.

## Architecture

- **Device layer (`device.py`)**: the only module touching `pymobiledevice3`/AFC. `scan()` does one pass (listdir + one stat per new entry, not `afc.walk`), takes `kinds` so unwanted kinds cost no round trips, and a `known` memo (path -> size/mtime; the Mac agent persists it in `mac_agent/scancache.py`) so rescans only stat new files. Lists `DeviceFile`s (kind = photos|videos|files, mtime in UTC) over USB, falling back to usbmux "Network" devices. Tests replace it with a `FakeAfc` (`tests/conftest.py`), so new device behaviour should go through it. The Mac agent reuses it as-is.
- **Catalog (`catalog.py`)**: cached phone listing (persisted so previews are instant on reconnect), `Filter` and `Selection` models. A selection is either explicit `paths` or "everything matching the filter minus `exclude`".
- **Importer (`importer.py`)**: one background import job at a time, with progress (bytes, speed, ETA), pause/cancel/retry. Dedupes by source path and by SHA-256; never deletes from the phone (the only phone-side delete is the Mac agent's opt-in, verified `agent.delete_from_phone`, which keeps Favourites and, only on the user's explicit `skip_verify` choice with a server down, skips the server check). `store_file` is the single place a finished file enters the library (uploads use it too).
- **Library (`library.py`)**: per-kind SQLite catalogs (`db/photos.db`, `videos.db`, `files.db`), destination-folder validation (`safe_folder`), classification. Existing DBs migrate on `init_library()`.
- **Watcher (`watcher.py`)**: lifespan task polling for the device; on connect refreshes the catalog and optionally auto-imports; publishes state to the UI via SSE (`/api/events`, consumed by `frontend/src/hooks/useLive.js`).
- **Uploads (`uploads.py`)**: chunked, resumable receiver (`init` → `PUT ?offset=N` → `complete`, which also accepts the sender's sha256 and rejects a mismatch; `POST /check` answers which items a client already sent). Used by the Safari page and the Mac agent; a future native app should reuse the same contract. Dedupe key is `device_id = app:<client_id>`, `device_path = app:<local_id>`.
- **Mac agent (`backend/mac_agent`)**: CLI that reads a USB iPhone via `app.device` and pushes it through the upload contract (`client_id = mac-<UDID>`, `local_id` = phone path); `--ui` serves a local browser screen (`ui.py` + `ui.html`: worker thread running `sync`, page polls `/api/state`; guarded by a Host check and a per-run `X-UI-Key`). `agent.sync` takes any `httpx.Client`, so `tests/test_mac_agent.py` drives the real app via `TestClient`.
- **Mac app (`backend/mac_app`)**: pywebview window + NSStatusItem menu-bar item around `mac_agent.ui.create_app` on a free loopback port (agent code untouched), `awake.py` runs `caffeinate` while `job.running`, `login.py` toggles a LaunchAgent. Built by `./build_app.sh` with PyInstaller in `backend/.build-venv` (py2app failed on python.org's `_ssl.so`; `cryptography<45` because newer wheels link Homebrew OpenSSL). The bundled `ui.html` needs `--add-data`.
- **Cloud relay (`backend/relay`) and home agent (`backend/home_agent`)**: multi-user staging service for uploads from anywhere (its own FastAPI app, SQLite in `RELAY_DATA`, or PostgreSQL when `DATABASE_URL` is set via `deployment/docker-compose.postgres.yml`; `relay/db.py` adapts one SQLite-dialect query set to both, and relay tests run on both; deploy with `deployment/docker-compose.relay.yml`, see `docs/runbooks/DEPLOY_RELAY.md`). Same `/api/upload/*` contract as `uploads.py` (plus `GET /api/uploads/pending` and `DELETE /api/upload/{id}` so a sender can list and discard uploads the agent has not collected), but every row is scoped by `user_id`; `user` tokens send, `agent` tokens only list/download/ack (`/api/relay/*`). The agent pulls outbound-only, verifies SHA-256, stores via `importer.store_file`, then acks (relay deletes the bytes, keeps a dedupe record). Optional end-to-end encryption (`relay/crypto.py`, X25519 + ChaCha20-Poly1305 chunks; `relay/sender.py` is the reference sender); the agent re-derives name/kind/folder itself because the relay is untrusted. Support chat (`relay/chat.py`: one conversation per account, phone endpoints under `/api/support/*`, console routes under `/internal/v1/support/*`, 90-day retention setting) is plain text, not the E2E path. Plans and decisions: `docs/guides/DEVELOPER_GUIDE.md` section 7 (the original phase plans are in `docs/archive/`). Not deployed or used on real hardware yet.
- **iPhone app (`ios/`)**: `BackupKit` is a Swift package (`Sealer` = the Swift side of `relay/crypto.py`, `RelayClient` = auth, pairing with a pinned agent-key fingerprint, the resumable `Uploader` and `BackupRunner`); `PhoneBackup` is the SwiftUI app (PhotoKit in `PhotoLibrarySource.swift`; new files must also be added to `project.pbxproj` by hand) and `PhoneBackup.xcodeproj` links the package. It talks only to the relay. A phone joins by scanning a QR from the home agent: `--invite` (`iphonebackup://enroll?relay&code&key`, carries a reusable bearer invite code, parsed by `EnrollLink`) or `--pair` (`iphonebackup://pair?relay&key`, no secret; the app then asks for email and password and pins the QR key only if the relay offers it): `/api/auth/enroll` gives it its own token on the PC's account and the QR carries the agent key to pin; "Remove this phone" uses `DELETE /api/auth/session` and must never call `DELETE /api/account` (that deletes the shared account). The Sent tab reads `SentLedgerStore`, the phone's own record, not the relay. Keep Swift and Python crypto byte-compatible: vectors in `BackupKit/Tests/SealerTests/Vectors` come from `tools.make_test_vectors`. Keychain needs a signed (ad-hoc is fine) build; with `CODE_SIGNING_ALLOWED=NO` sign-in fails with a generic error. Planned app changes (Share extension, Auto sync, Library viewer, retry/discard) are tracked in `docs/archive/PLAN_APP_ENHANCEMENTS.md`; the library-browse-from-phone protocol is only a draft (`docs/specs/BROWSE_CONTRACT.md`). Progress and requirements (originals and Live Photos, robust transfers) are in `docs/specs/PLAN_IOS_APP.md` and `docs/SYNC_NOTES.md`.
- **Operator console = three separate deployables** (`docs/specs/PLAN_ADMIN.md`): the **client relay** (public; phones and home agents), the **admin backend** (`backend/admin_service`, own FastAPI app on :8780, own database, own sign-in with password + authenticator code, roles, audit, rate limits and a network allowlist that makes everything 404 for other addresses) and the **admin frontend** (`admin-frontend/`: static `index.html` + `app.js` + the committed `crypto.js` bundle, served by nginx, which forwards `/api` to the backend). The admin backend reaches the relay only through its internal API (`relay/internal.py`, `/internal/v1`, shared `RELAY_INTERNAL_TOKEN` of 32+ characters, blocked by Caddy, switched off when unset); the relay knows nothing about admins and the admin side owns no customer data, so a break-in on one does not give the other. Nothing in either can name a file or folder. Support access: the owner makes an access code on the box (`home_agent --grant`), the browser seals a request with it (`admin-frontend/crypto-src/entry.js` mirrors `relay/support_proto.py`; rebuild `crypto.js` with `crypto-src/build.sh`), the relay only queues sealed bytes and `home_agent/grants.py` answers (blind copy/rename, padded). `dbkit/` is the small SQLite/PostgreSQL layer both services use. Deploy the admin plane with `deployment/docker-compose.admin.yml`. Operations features (approvals/maker-checker, admin management with an owner flag, audit search+CSV, system and usage views, runtime relay settings, announcements, waitlist + sign-up codes, maintenance, account export/purge, tickets/notes, runbook) are modules beside `main.py` (`approvals.py`, `admins_mgmt.py`, `reports.py`, `comms.py`, `tickets.py`; each adds routes to `app`), the relay's `internal_ops.py` + `settings.py`, and `admin-frontend/features.js`; the Support inbox (`support_inbox.py` + `admin-frontend/support.js`) is the operator side of the in-app chat; see the table at the end of `docs/specs/PLAN_ADMIN.md`.
- **Thumbs (`thumbs.py`)**: on-disk thumbnail cache (`.thumbs` for library, `.devthumbs` for phone files), reset on disconnect.
- **Auth (`main.py`)**: loopback is trusted; any other client on `/api/*` must send the pairing token (`X-Token` header or `?token=`). Endpoints exposing the token/settings use `local_only()`. The web UI (`api.js`) prompts for the token once, keeps it in `localStorage`, and appends `?token=` to image/video/SSE URLs that can't send headers.

## Docker and storage

- **All Docker and deployment files live in `deployment/`**: the Dockerfiles, `docker-compose*.yml`, the `docker/` configs (nginx, Caddy), and the PC scripts (`deploy-watch.ps1`, `install-*.ps1`, `relay-local-up.ps1`, `sim-boxes-up.ps1`, `testenv-up.ps1`, `make_client_cert.sh`). The build context is still the repo root (`context: ..`, `dockerfile: deployment/Dockerfile.x`), and `.dockerignore`, `.env*.example`, `start.*` and `config/` stay at the root. Run compose from the **repo root** as `docker compose -f deployment/docker-compose.yml ...`. Compose reads `.env` from the compose file's folder, so pass the PC's root `.env` explicitly with `--env-file .env` (`deploy-watch.ps1` does). Each compose file pins `name:` so project and volume names (`iphonebackup_iphone-data`) did not change with the move.
- `deployment/Dockerfile.backend` (API only) and `deployment/Dockerfile.frontend` (nginx serving `dist`, proxying `/api` to `backend`, buffering off for SSE, no upload size limit) are wired by `deployment/docker-compose.yml`. The backend does not serve the UI in this setup.
- **Storage is split.** Media files: bind mount of the Windows folder at `/library` (`LIBRARY_ROOT`; `LIBRARY_DIR` overrides the host path). Metadata (`db/*.db`, `.thumbs`, `.devthumbs`, `.cache`): Docker volume `iphone-data` at `/data` (`DATA_ROOT`, from `IPHONE_DATA`). `.tmp` stays with the media because finished uploads are moved into the library. Without `IPHONE_DATA`, `DATA_ROOT` falls back to `LIBRARY_ROOT`, so native runs are unchanged.
- **Behind Docker's port mapping nothing looks like loopback**, so every request needs the token. Compose sets `TOKEN_IS_ADMIN=1` so a valid token may use `local_only` endpoints (pairing, settings); without it those stay PC-only.
- The token lives in `config/settings.json` (gitignored; `SETTINGS_FILE` points at it from compose, `start.ps1` and `start.sh`), so Docker and a native backend share one token. A machine without the file generates its own.
- The pairing QR uses `PUBLIC_URL`, else the `Host` the browser used (nginx forwards `$http_host`), else the container's LAN IP, which is wrong in Docker. Open the UI via the PC's LAN address.
- **Public HTTPS (optional)**: `caddy` service (profile `public`, `deployment/Dockerfile.caddy` = Caddy + DuckDNS DNS-challenge plugin, `deployment/docker/Caddyfile`) publishes only `/api/upload*` and `/api/device` on 443 (80 redirects). Enabled by `COMPOSE_PROFILES=public` + `DUCKDNS_TOKEN` in the PC's gitignored `.env`; without them compose is unchanged. Optional mutual TLS: `make_client_cert.sh` (run on the Mac) makes the CA + client cert; `config/mtls/ca.crt` on the PC and `MTLS_SNIPPET=/etc/caddy/mtls.conf` make Caddy require it (`deployment/docker/mtls.conf`); `mac_agent/tls.py` presents `~/.iphone-backup-mtls/client.{crt,key}` automatically. Caddy parts untested on the real PC.
- `deploy-watch.ps1` (a scheduled task) polls `origin/main`, fast-forwards, and runs `docker compose -f deployment/docker-compose.yml up -d --build`. It only fast-forwards and **skips the update while tracked files are modified or local commits are unpushed**, so commit and push before expecting a redeploy. It logs every poll to `deploy-watch.log`, removes leftover `<hex>_name` containers from an interrupted `compose up`, and retries a failed deploy once.

## Two machines, one branch

- **A new Claude session has no memory of earlier ones. Always, as your very first step: `git pull`, read `docs/SYNC_NOTES.md` sections *Start here*, *Open requests* and the newest Log entries, and tell the user what you found before starting work.** Never rely on assuming what a previous session did; the Log is the record. When you finish or the user switches machine, write a Log entry (tried / worked / failed / pending), update *Open requests* and the *Durable facts*, commit and push.
- The Mac (iPhone app in `ios/`, `backend/tools/`) and the Windows PC (Docker relay and home agent) hand work to each other through `docs/SYNC_NOTES.md`. **At the start of a session `git pull` and read its *Open requests*; before every commit you will push, add a Log entry, update the requests and the matching rows in `docs/project/PENDING.md` (and `docs/project/FEATURES.md` when something lands); push right after committing.** Never put secrets in it. Contract changes (`backend/relay/`, `crypto.py`) must be flagged there and the Swift test vectors regenerated (`python -m tools.make_test_vectors`).

## Gotchas

- Relay/home-agent compose commands must run from the **repo root** (`.env.relay-local` is found relative to it; from `backend\` they fail with "couldn't find env file"). Test against a throwaway relay (`uvicorn relay.main:app --port 8771`, `RELAY_DATA=<temp>`), not the real one on :8770.
- The relay has no change-password endpoint, and `.env.relay-local` (gitignored, holds the account credentials) must match what the phone signs in with. Never print or commit it.
- Plain-HTTP pages lack secure-context APIs (`crypto.randomUUID`, Wake Lock); use `crypto.getRandomValues`. Every client request needs a timeout, and a retry must first re-ask the relay how much it has (`POST /api/upload/init`).

- `backend/app/main.py` calls `init_library()` at import time; tests set `IPHONE_LIBRARY` to a temp dir *before* importing the app (`conftest.py`), so keep that ordering. Paths are `.resolve()`d because macOS temp dirs sit behind `/var` → `/private/var`.
- Dates and the default `<year>/<full month name>` folders (e.g. `2026/October`, `library.auto_folder`) come from the phone file's mtime, not EXIF (deliberate, for scan speed).
- A file already imported is skipped even when re-imported into a different folder; identical content (SHA-256) is stored once.
- On Windows the working tree is checked out with CRLF (git warns on every commit); shell scripts such as `start.sh` are committed with LF, so don't "fix" them.
- `server.log` and `deploy-watch.log*` are runtime logs (gitignored). Never commit `config/settings.json`.
